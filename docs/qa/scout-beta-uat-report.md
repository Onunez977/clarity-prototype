# Scout Beta (scanner-app) — Consolidated UAT & Bug/Gap Audit

Clarity Scout (a.k.a. Scout Beta) is a triple-gated, experimental driver-facing PWA layered onto the Clarity LPR platform: it gives field repo drivers a Vue/Pinia mobile app (token-authed against `/api/scout/*`) with a live Google Maps view of their assigned zones, scan-path density, trips, dashboard stats, real-time zone-assignment push over private broadcast channels, and an end-of-shift email summary — administered through Filament admin surfaces (Manage Zones, Scout Users) and a `kit_id → kit_settings` data refactor. This report merges three workstreams into one audit: **DEV-1916** (developer-side QA of the feature build), **DEV-1921** (staging click-through UAT), and **DEV-1925** (the zone-coverage visibility story). Every finding below was adversarially verified against the code on the `scanner-app` branch (file:line references are drawn directly from the source), and the test matrix reflects authored UAT cases cross-checked against the existing automated suite.

## 1. Executive summary

**Feature scope**
- A token-authenticated Scout PWA (login, dashboard, live map, trips, profile) served only when the Scout config flag is on, gated per-org by a Pennant feature and per-user by the `clarity-scout` permission plus an assigned kit.
- Admin surfaces: **Manage Zones** (Google-Maps polygon/ZIP zone editor with driver assignment + real-time push) and the edit-only **Scout Users** resource (kit↔user binding, vehicle type, onboarding, force-login impersonation).
- A `users.kit_id` → `platform.kit_settings` refactor that moves the kit↔user link and per-kit vehicle type into derived accessors.
- Real-time zone push (added/removed/updated/deleted) over per-user private channels, backed by persisted bell notifications.
- Lazy-materialized shifts with a ClickHouse + PostGIS end-of-shift summary email.

**Ship-readiness verdict: Not ready (ship-with-fixes after the high-severity items are resolved).** The backend is broadly well-tested and the gating model is sound, but there are multiple confirmed high-severity correctness/UX defects (non-transactional zone save with broadcast-before-rebuild, set-password not actually logging the driver into the PWA, force-login evicting live drivers, and a dashboard missing two DEV-1916 §8 acceptance items), plus the entire Vue/PWA layer has zero automated coverage.

**Top blockers / high-risk items (highest severity first)**
1. **High — Zone save is non-transactional and broadcasts "added to zone" before geometry is rebuilt** (`app/Filament/Pages/ManageZones.php:261-272`). A PostGIS/Tiger failure leaves a committed zone with null/stale geom after drivers were already attached + notified; newly-assigned drivers refetch a `geometry:null` feature.
2. **High — Set-password success does not log the driver into the PWA** (`app/Http/Controllers/Auth/ScoutSetPasswordController.php:43-46`). It does a web-session `Auth::login` but the PWA only reads a Sanctum token; the driver lands on the login screen and must re-enter the password they just set.
3. **High — Admin force-login revokes the driver's live token, kicking them out mid-shift** (`app/Http/Controllers/ClarityScoutForceLoginController.php:20`). Shared `clarity-scout-token` name collision evicts the on-shift driver.
4. **High — Dashboard omits the Recent Hits list and Hotlist stats card required by DEV-1916 §8** (`resources/js/clarity-scout/views/Dashboard.vue:72-109`); both endpoints exist and are routed but never consumed.
5. **High — New shift's inferred `started_at` can overlap the previous closed shift** (`app/Services/Scout/EnsureOpenShift.php:134-171`), double-counting miles/scans/hits across a confirmed End-Shift.
6. **High — Granting Scout access via the list-page toggle never sends an onboarding/set-password email** (`app/Filament/Resources/ScoutUsersResource.php:358-396`), locking the user out with an unknown random password and no resend path.

**DEV-1925 status:** Definitively **not implemented** on this branch — no covered-vs-missed coverage layer, no honey-hole/high-value zone-scoped toggle, and no configurable lookback; only adjacent-but-different features exist (scan-path frequency coloring, org-wide hit/hotlist heatmaps).

## 2. Scope & gating

Clarity Scout is protected by a **triple gate** enforced consistently across the API, broadcast channels, admin Filament surfaces, and the scheduler:

1. **Global config flag** `app.experimental.clarity_scout` (env `CLARITY_SCOUT_ENABLED`, default `false` — `config/app.php:166`). This is the master switch: it wraps route registration itself. `routes/api.php:15` wraps the entire `/api/scout/*` group **and** `/api/broadcasting/auth` in `if (config('app.experimental.clarity_scout', false))`; `routes/web.php:99-110` wraps the scout force-login, signed set-password, and the `scout/{any?}` PWA catch-all. When off, the routes are never registered and `web.php:158`'s `Route::any('{any}')->redirect('/app/login')` swallows scout URLs.
2. **Pennant feature** `platform_repo_pro_clarity_scout` (`FeatureEnum::CLARITY_SCOUT`, slug `clarity-scout` — `app/Enums/FeatureEnum.php:77-84`), resolved per-org. Note: two known per-org bypasses exist — the time-boxed Pro Trial backdoor (`User::isProEnabled`, expired window Feb–Apr 2026) and the `@insightlpr.com` email bypass (`PennantServiceProvider.php:42`).
3. **Spatie `clarity-scout` web permission**, seeded outside the vendor PermissionEnum by `SeedRolesAndPermissions` (`app/Console/Commands/SeedRolesAndPermissions.php:50`), scoped to the org team id.

The runtime API gate is `ClarityScoutMiddleware` (401 unauth → bypass-all if the token carries the literal `clarity-scout-force` ability → `clarity-scout` permission 403 → kit 403 → active feature 403). The login endpoint re-implements the same checks pre-token. Broadcast channel auth (`routes/channels.php:19-45`) mirrors the middleware under the Sanctum guard.

**How to enable Scout for an org:** set `CLARITY_SCOUT_ENABLED=true` (config flag on), activate the `platform_repo_pro_clarity_scout` Pennant feature for the org (or use a trial/internal bypass), seed the `clarity-scout` permission, grant it to the driver, and assign the driver to a kit via `kit_settings`. Admin surfaces additionally require the ADMIN role.

**Test-data prerequisites:**
- **Two orgs** — Org A (flag + feature on, the positive path) and Org B (flag/feature off, the negative-gating path) for multi-tenancy isolation checks.
- **Kits with and without an assigned scout user** (via `kit_settings`), to exercise assigned vs. "Unassigned" rendering and the no-kit 403 gate.
- **Scout users with and without an email** (onboarding email vs. "Email Required"), and verified vs. unverified (onboarding-send gating).
- **Activity vs. zero-activity kits** — kits with scans/hits/trips inside assigned zones (for shift summaries, density, per-zone breakdown) and a zero-activity kit (empty-state shift summary).
- **PostGIS + `tiger_data.zcta5_all`** present on the `zod` connection (ZIP-zone geometry, per-zone breakdown).
- **Pusher/Echo** configured so channel-auth callbacks actually run (Log/Null broadcasters no-op auth).

## 5. DEV-1925 — zone coverage visibility (gap + readiness)

**Status: DEFINITIVELY NOT IMPLEMENTED on the scanner-app branch.** This was verified by reading all key files plus `routes/api.php` and the existing map/query tests, and by grepping the entire `resources/js/clarity-scout` tree and the three ClickHouse queries for `coverage|covered|uncovered|missed|honey-hole|lookback|grating|high-value` — the only matches are cosmetic (a "Live coverage map" Profile hint, a Help.vue paragraph describing the existing density coloring, and one code comment "density coverage from kit_trips"). There is no route, store field, map layer, toggle pill, or test for covered-vs-missed coverage, a zone-scoped honey-hole layer, or a configurable lookback. The "ABSENT" finding is **confirmed**.

**Each acceptance criterion is UNMET:**
1. **"A driver can view their assigned Zone on the map"** — *partially met as context only.* Assigned zones DO render (`stores/map.js:207-229` fetchZones; `ScannerMap.vue:722-743`), but as a decorative colored polygon, not the interactive coverage surface the rest of the story builds on. This is the only AC with any backing code.
2. **"The map shows the driver's own recent scan coverage within the Zone, with a configurable lookback window (default 30 days)"** — *unmet.* No per-driver, zone-clipped coverage layer and no 30-day-default configurable lookback exist (`ClarityScoutMapController.php:21-74`, `getDateRange:313-325`; `routes/api.php:38-42`).
3. **"Covered vs. uncovered (missed) areas within the Zone are visually distinguishable"** — *unmet.* Zones render as a uniform flat fill (`ScannerMap.vue:716-778`); nothing subdivides them by covered/missed and no layer is clipped to the polygon.
4. **"The driver can toggle map layers to surface high-value areas / hotspots (honey holes)"** — *unmet.* Exactly three fixed heatmap pills exist (`ScannerMap.vue:203-207`; `stores/map.js:78-109`), all org-wide and not zone-clipped, none a zone-scoped prioritization layer.
5. **"Coverage and layer data refresh as new data comes in"** — *unmet/moot.* No coverage layer to refresh; the adjacent heatmaps only refetch on map-idle/bounds-change and are server-cached 5 minutes (`ClarityScoutMapController.php:95,347`; `stores/map.js:263-266`).
6. **"Supports complete Zone coverage even when no hotspots are present (grating)"** — *unmet.* Every layer is hotspot/activity-driven; with no hotspots a driver gets no signal of which parts of the zone are still unscanned.

**Adjacent-but-different features that exist (do not mistake for DEV-1925):**
- **Scan-path FREQUENCY coloring** — `ClarityScoutMapController::buildDensitySegments()` (`app/Http/Controllers/Api/ClarityScoutMapController.php:213-308`) colors a driver's own trip paths green→red by how OFTEN ~100m grid cells were driven. This is path repetition — the conceptual inverse of covered-vs-missed — with fixed date buckets, no configurable lookback, and no zone clipping.
- **Hit-density heatmap of hotlist hits** — `HitDensityGeohashQuery` (`app/Clickhouse/Queries/HitDensityGeohashQuery.php`) geohash-buckets hotlist HITS org-wide with a HARDCODED 9-month cutoff (`now()->subMonths(9)`, line 28), surfaced as the "Hit Hotspots" pill — org activity, not driver coverage, not zone-clipped.
- **Hotlist-address heatmap** — `HotlistAddressGeohashQuery` buckets open hotlist ADDRESS locations with NO time filter, surfaced as "Direct Orders"/"Staging Orders" pills.
- **Scout check-in rollup** — `ScoutCheckInRollupQuery` feeds dashboard Direct/Staging COUNT cards (scalar counts within ~160m of open-hotlist addresses), not a map layer or coverage window.

**Readiness notes / open questions (must be answered before implementation):**
- What defines a **Zone boundary** and how is it assigned/managed? (Today: `app/Models/Zone.php` polygon or ZIP-derived geometry via `tiger_data.zcta5_all`, assigned via the `zone_user` pivot; the coverage query must clip to this geometry — which depends on PostGIS + Tiger data being present.)
- What is the **unit of "coverage"** — roads/segments driven, area grid cells, or scan density? (Determines whether to reuse `kit_trips` path data, a geohash/H3 grid, or scans.)
- What data defines a **"honey hole"/hotspot** — hits, recoveries, or historical scan density? (The existing hit heatmap uses a 9-month cutoff; the address heatmaps use open hotlist addresses; none is zone-scoped.)
- Is coverage **per-driver or shared** across all drivers assigned to the zone? (The story implies per-driver "your own" coverage.)
- Confirm **30 days as the default lookback** and whether/how it is adjustable (no lookback control exists today).

A future build would need: a new ClickHouse query computing the driver's own scan/trip coverage as a grid clipped to the zone, parameterized by a default-30-day lookback **and** representing the MISSED set; a new org-isolated `/api/scout/map/coverage` endpoint scoped to kit + assigned zones; a new toggleable map layer + lookback control + covered-vs-uncovered rendering in the PWA; refresh wiring reusing the existing 20s poll / on-move pattern; a zone-clipped reframing of the heatmaps for the honey-hole AC; and backend tests (the Vue/PWA layer would remain human-only QA).
