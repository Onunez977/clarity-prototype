Plan: implementation plan for DEV-2928

Approach
- New operator command `app:rdn-backfill-branches {org} --since= [--until=] [--chunk=500] [--max=] [--dry-run=N]`. It selects the org's RDN hotlists that had activity in the window: a status-log transition or repo_date in the window, or currently Open/Hold. It skips rows that are already resolved or sealed, using the existing `sealedPredicate()`. It walks newest first and pushes the existing `GetOrgHotlistCaseInfo` job onto a dedicated `{rdn-backfill}` queue, one chunk at a time, only while that queue is shorter than one chunk. A per-org/window cursor makes it resumable, and the unique lock plus the attempt ceiling make it safe to re-run. `--dry-run=N` samples the <30d / 30–180d / >180d buckets, calls RDN directly, and writes nothing.
- `GetOrgHotlistCaseInfo` keeps its dispatch contract, rate limit, uniqueness, miss ceiling and counters. The only change: its inline branch lookup moves into one static `findBranch()`, which tries the exact match first and then a normalized fallback (trim, case-insensitive, collapse whitespace/punctuation). The dry run reuses it, so no new service is needed.
- LPR Assists and Missed Opportunities filter by the hotlist's current branch at query time when a branch is selected, using the same `clarity.hotlist FINAL … ifNull(branch_id, 0) = ?` subquery as the transition cards. The LPR filter keys on `recovery_id`, which is the hotlist id (evidence in the spec). The unfiltered (All Branches) SQL does not change.
- No ClickHouse writes, no MV/schema changes, no production or fleet backfill run from this work.

Blast radius

- Data: PostgreSQL reads (hotlist, hotlist_json, hotlist_meta, hotlist_status_log, orgs, org_meta, branches) plus the existing job's hotlist_json writes. ClickHouse: read path only. Migrations: no. Routes: none. Config: config/horizon.php only.
