## 1. Summary and intent
DEV-2442 (PR #374) restored the forward-only RDN case-info enrichment. That job writes `hotlist_json.branch_id`. PR #374 also moved branch-filtered status cards onto `HotlistStatusTransition` with a read-time `clarity.hotlist FINAL` branch join. Existing hotlists still have no `branch_id`, so a branch filter shows only recent data. On top of that, LPR Assists and Missed Opportunities filter on a `branch_id` that was copied onto `clarity.recoveries` / `clarity.missed_opportunities` when each row was written, so a branch that arrives later never reaches them.

This ticket ships four things:
1. An operator command, `app:rdn-backfill-branches {org}`. It walks one org's RDN hotlists that had activity in a window, newest first, and runs `GetOrgHotlistCaseInfo::handle()` inline for each (same RDN call / Branch match / writes / outcome counters), one call at a time under the job's own `rdn-case-info` limiter bucket. A resumable cursor is saved after each chunk. Nothing is queued. A `--dry-run=N` mode samples RDN and writes nothing.
2. A normalized branch-name fallback that runs after the exact match fails, inside the job's existing branch lookup.
3. Query-time branch filtering for LPR Assists and Missed Opportunities on the hotlist's current branch: `IN (SELECT id FROM clarity.hotlist FINAL WHERE org_id = ? AND _peerdb_is_deleted = 0 AND ifNull(branch_id, 0) = ?)`. Unfiltered SQL does not change.
4. A runbook in the PR body.

### Resolving the "unchanged job + normalized match" tension
Jira says to reuse `GetOrgHotlistCaseInfo` "unchanged (per-org RDN rate limit, uniqueness lock, miss ceiling, outcome counters)" and also to add normalized matching. Normalized matching has to live in that job's branch lookup (`app/Jobs/Rdn/GetOrgHotlistCaseInfo.php` L360–365). This spec takes the smallest reading:
- These stay byte-for-byte on the job itself: the constructor and its `onQueue('{low}')` (production dispatch only — the backfill never pushes), `middleware()` / `RateLimited('rdn-case-info')`, `uniqueId()`, `retryUntil()`, `sealedPredicate()` / `maxLookupAttempts()`, the outcome constants, `recordOutcome()`, `writeBranchId()` and `recordUnresolvedLookup()`. The backfill calls `handle()` in-process.
- Only the inline `Branch::where(...)->where('branch_name', …)->orderBy('id')->first()` block moves into one `public static function findBranch(int $orgId, string $vendorBranchName): ?Branch` on the same class. It keeps the exact match first, then tries a normalized fallback. `handle()` calls it. The dry run calls it too.
- Why not a service or a trait: the dry run needs exactly this one lookup, without writes. A static method on the class that already owns the lookup is the smallest shared seam, and it keeps the match logic next to the outcome semantics it feeds. A new service or trait would break hard stop #24. A `Branch` model scope does not fit either, because exact-then-fallback is two queries.
- The dry run maps outcomes with the job's own `OUTCOME_*` constants, using the same three-way rule as `handle()` (L355–390): resolved, else `! lastCallCompleted()` → transport_failed, else miss_no_branch_match if RDN named a branch, otherwise miss_no_branch_name. A test pins the dry-run classification against the job's.

Enrichment job (from PR #374)
- `GetOrgHotlistCaseInfo` is `ShouldBeUniqueUntilProcessing` with `uniqueId() = hotlistId`. `uniqueFor` and `retryUntil` are both spread + drain = `case_info_run_interval_minutes` × 2 = 48h at the shipped 1440 (`app/Jobs/Rdn/GetOrgHotlistCaseInfo.php` L254–275, L319–324; `config/services.php` `rdn.case_info_run_interval_minutes`).
- The constructor hard-sets `onQueue('{low}')` for the job's normal production dispatch. The backfill does not push the job; it calls `handle()` in-process. Leave the constructor alone.
- The job has a kill switch. `isEnabled($forced)` is checked at the top of `handle()` (L245, L326+). If `services.rdn.case_info_enabled` is off, every backfill job no-ops, so the command must refuse to run (otherwise the cursor would advance over unprocessed rows).
- "Resolved/sealed" means `sealedPredicate()` bound with `maxLookupAttempts()`: branch_id IS NOT NULL, or attempts ≥ ceiling (L34, L97–131). `GetOrgHotlistCases` excludes rows with `whereDoesntHave('hotlistJson', sealedPredicate)` (`app/Jobs/Rdn/GetOrgHotlistCases.php` L232). Copy that.
- Eligibility to copy from `GetOrgHotlistCases::candidates()` (L350–358): `integration_id = RDN`, `remote_order_id IS NOT NULL`, `status IN ANALYTICS_STATUSES` (L49–57; excludes Invalid 99). Drop only its `created_at >= lookback` clause and replace it with the activity predicate.
- The scheduled `GetOrgHotlistCases` dispatch shape (UniqueLock + Dispatcher) is **not** used by the backfill (inline rewrite). The backfill builds `GetOrgHotlistCaseInfo` and calls `handle()` in-process, counting processed/failed and logging `rdn.backfill_branches.failed` on a throw. The run summary still uses `Log::info` in `finally` (PG-025).
- Rate limit: `RateLimited('rdn-case-info')` is per org, `Limit::perMinute($org->rdnRateLimit())` (`app/Providers/AppServiceProvider.php` L118–119; default `services.rdn.default_rate_limit` = 100). The inline backfill waits on and hits this same bucket: limiter resolved by name for the job, key `md5('rdn-case-info'.$limit->key)` = `md5('rdn-case-info'.'rdn-case-info:{org}')`, the formula `Illuminate\Queue\Middleware\RateLimited` uses (`vendor/laravel/framework/src/Illuminate/Queue/Middleware/RateLimited.php` L78). Combined case-info traffic stays within the org's limit, and the shared `rdn-api:{org}` bucket (sibling RDN jobs, web `Org::getRdnClients`) is untouched. **Wiki conflict:** `okf/concepts/rdn.md` says the job reuses `RateLimited('rdn-api')`. Code says `rdn-case-info`.
- The current exact match is `Branch::where('org_id')->where('branch_name', $vendor)->orderBy('id')->first()`, and the job writes `$branch->branch_id` (the external RDN branch id, not `branches.id`) (L360–365). The Client Analytics branch selector uses the same key: `branches->pluck('branch_name', 'branch_id')` (`app/Filament/Pages/ClientAnalytics.php` L137).
- The `recordOutcome()` docblock says "the branch match is exact string equality … has never run in production". Update that sentence when adding the fallback.

ClickHouse read path
- Template is `HotlistStatusTransition`. `scopeForOrg` stashes the org id on the query builder because CH rejects correlated IN (`app/Clickhouse/Models/HotlistStatusTransition.php` L26–32). `scopeForBranch` returns early on null/0 and otherwise adds `hotlist_id IN (SELECT id FROM hotlist FINAL WHERE org_id = ? AND _peerdb_is_deleted = 0 … AND ifNull(branch_id, 0) = ?)`; it throws if `forOrg` was not called first (L57–84). Our version omits the transitions' `created_at <= window_end` bound on purpose (see below).
- `LprAssist::buildWhereClause` currently adds `AND r.branch_id = {$branchId}` (`app/Clickhouse/Models/LprAssist.php` L31) on `clarity.recoveries r FINAL`, joined `r.id = la.recovery_id` (L63–65). The file qualifies tables as `clarity.*`, so the new subquery should use `clarity.hotlist`.
- `MissedOpportunity::scopeForOrg` filters `hotlist_org_id` (the hotlist owner = `clarity.hotlist.org_id`), and `scopeForBranch` is `where('branch_id', …)` (`app/Clickhouse/Models/MissedOpportunity.php` ~L27–30, ~L49–52). The model is Eloquent-scoped like `HotlistStatusTransition`, so use unqualified `hotlist FINAL`. Metric is `countDistinct(hotlist_id)` (`okf/concepts/missed-opportunity.md` "Rules").
- Schema (no edits): `clarity.hotlist` has `branch_id Nullable(Int64)`, `ReplacingMergeTree(_version, _peerdb_is_deleted)`, `ORDER BY (toYYYYMM(created_at), org_id, created_at, id)` and skip index `idx_branch_id set(1000)` (`database/schema/clickhouse-schema.sql` L24). `clarity.missed_opportunities.branch_id UInt32 DEFAULT 0` (L33). `clarity.recoveries.branch_id Nullable(Int64)`, `ORDER BY (org_id, repo_date, id)` (L34). `clarity.recovery_scans` is at L38. The view `clarity.lpr_assists` is at L89. `clarity.hotlist_incremental_mv` is `REFRESH EVERY 1 MINUTE APPEND TO clarity.hotlist` (L104).
- Why there is no `created_at` window bound in the new subquery: for MO, historical (`F`) hits come from `find_historicals()` scans that predate hotlist creation (`okf/concepts/missed-opportunity.md` "Hit types M and F"; `okf/concepts/hit.md`). A `hotlist.created_at <= window_end` bound would drop real rows. The ticket's predicate has no bound, so keep it unbounded and measure (Q3). Cost reference: the transition join measured 508MB/556ms per month window on org 165 *with* a window bound (`docs/investigations/DEV-2442/journal.md` 2026-10-07 09:12).
- PG-024 (`okf/concepts/platform-gotchas.md`): `org_id` is the second key in `clarity.hotlist`'s ORDER BY, after `toYYYYMM(created_at)`, so an org-only predicate prunes poorly. That is exactly what the #25 measure has to quantify.
- Wiki conflict: `okf/models/clickhouse/lpr_assists.md` says the filter uses `r.repo_branch_id`, but code uses `r.branch_id` (LprAssist.php L31; `tests/Unit/Clickhouse/LprAssistBranchFilterTest.php` L20–21).
