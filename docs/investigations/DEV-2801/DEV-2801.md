## 1. Summary and intent

`LprRepossessionsQuery` decides whether a billed case claim went on to a recovery. To do that it joins hotlists twice:

1. `zod.public_hotlist FINAL` (status = 3, not deleted) matched on `(agent_org_id, vin)`. This leg answers "does this claim match a repossessed hotlist".
2. `clarity.hotlist` (no FINAL, `{floor}` prefilter) matched on `id`. This leg supplies `first_repossessed_at` for the `>= claim_date - 7` predicate.

DEV-2660 (PR #470, merged, Done) shipped that shape on purpose. It swapped only the timestamp leg.

This ticket asks whether both legs can run off one `clarity.hotlist` join, which would drop the `public_hotlist` hop. That is not a timestamp-only swap. It moves the match semantics (status fence, delete fence, VIN, org) from a FINAL'd CDC mirror onto a denormalised MV target that is read without FINAL today.

The work comes in two stages:

- **Gate 1 is a measured decision.** It is not a refactor.
- **Keeping the dual-join is a valid, complete outcome.** Choose it if the measure fails or a CDC/FINAL/VIN/cardinality reason holds. Code changes happen only on the collapse path.

**`clarity.hotlist` schema facts that decide the collapse** (`database/schema/clickhouse-schema.sql`).
- L23, table:
  - It carries `org_id Int32`, `status Nullable(Int32)`, `vin Nullable(String)` and `first_repossessed_at Nullable(DateTime64(6))`, so a single join is expressible.
  - Engine `ReplacingMergeTree(_version, _peerdb_is_deleted)`, `ORDER BY (toYYYYMM(created_at), org_id, created_at, id)`.
  - TTL drops `_peerdb_is_deleted = 1` rows after 30 days.
  - Projection `prj_id_lookup_v2` (`ORDER BY id`) includes `status, vin, org_id, first_repossessed_at`.
- L102, `clarity.hotlist_incremental_mv`:
  - `vin` = `argMax(vin, _peerdb_version)` from `zod.public_hotlist`, with no normalisation. Parity of the un-normalised VIN is by construction, but it still has to be measured (M3).
  - The MV filters `WHERE h.org_id IN (SELECT id FROM clarity.orgs FINAL) AND h._peerdb_is_deleted = 0`. Two things follow:
    - (a) Coverage is limited to clarity orgs. That is answer-neutral for `db_repos`, because today's predicate already needs a `ch` row: an unmatched `ch` gives a NULL `first_repossessed_at` and is not counted.
    - (b) **The MV never emits a row for a hotlist whose latest public_hotlist version is deleted.** So a PG delete may never reach `clarity.hotlist` as a tombstone through this MV, and the earlier live row stays visible. Whether another writer (chlocal) emits tombstones is unverified; see §8 Q6. This is a concrete CDC risk for the collapse, which M2 measures.

**FINAL discipline (KB).**
- `okf/concepts/clickhouse-query-patterns.md` §"Use FINAL only where needed" (L80–99): `zod.public_hotlist` FINAL is **required**, because raw over-counts by 13.3%. The rule is "FINAL earns its cost only when the column you are reading is mutable across CDC versions". `status` is mutable.
- Today `clarity.hotlist` is read only for `first_repossessed_at`, which is near-immutable: a min(), with 0.187% re-entry per DEV-2657. That is why FINAL could be dropped there. A collapse would read the mutable `status` (plus the delete flag) off `clarity.hotlist`, which is the case the rule says needs FINAL.
- Precedent: other current-status reads of `clarity.hotlist` all use FINAL (`okf/concepts/scout-dashboard-stats.md` L53–55; `okf/concepts/hit.md` L66). The Eloquent model applies `ApplyFinal` globally (`okf/models/clickhouse/hotlist.md` §"Notable scopes & behavior").

**Sentinel discipline.** `okf/concepts/platform-gotchas.md` PG-030 (L286–307): under `join_use_nulls = 0` an unmatched LEFT JOIN yields type defaults (`0`, `''`), not NULL. Every consumed join key needs a sentinel guard, and the test must seed a row at the sentinel. Note that `clarity.hotlist.first_repossessed_at` is `Nullable`, so for an unmatched `ch` it reads NULL, while `ch.id` (Int64) reads 0.
