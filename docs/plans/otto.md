# Otto — Clarity AI Assistant Reference

> **Maintenance:** Update this file when Otto behavior, tools, prompt, widgets, events, or frontend change.

Otto is Clarity’s conversational LPR assistant on the **admin `/app` panel** only. It searches org-scoped scans, hits, and hotlist assignments, looks up Scout driver locations when available, searches and proposes Scout patrol zones, surfaces interactive widgets, and answers customer-safe product questions from `resources/otto-knowledge/`. Built on `laravel/ai`.

## Gates

- Org: Clarity Pro Lite or higher (`Org::proTier()` via `Org::ottoEnabled()`)
- Permission: Spatie `use-otto` (seeded by `app:seed-permissions`)
- Access helper: `App\Support\Otto\OttoAccess::userCanUseOtto`
- Staff impersonation (`admin_impersonator` session) may use Otto when the org is enabled (QA), including without `use-otto`. `OttoAccess::userCanUseOtto()` always `setPermissionsTeamId` first so a fresh impersonation request does not admit Otto with a null Spatie team
- Search / Apply* / detail tools gate on `OttoToolAuth::userCan` (set team id + drop stale `roles`/`permissions` relations) so Horizon reuse and the first impersonation turn still offer `ScanSearchTool` when `ViewAny_SCAN` is present. Otto must not be a wider door than the Filament policy — there is no impersonator bypass on those tools
- Conversation ids are never client-writable: HTTP send/stop/poll and `RunOttoChat` require the conversation to belong to the acting user
- Hydration: `GET /otto/investigation/{conversationId}` returns `searchIds[]` per row plus `drivers[]` from Scout position searches and `zones[]` (centroid plus compiled GeoJSON `geometry`) from zone searches; widgets match `(searchIds || []).includes(searchId)`. Detail cards listen for `otto.detail` with `result_type` / `result_id`
- Mount: App panel `->renderHook(LAYOUT_END)` → `components.otto.popout-mount` (`#otto-root` + `window.__OTTO_CONFIG__` + `@vite('resources/js/otto/filament.js')`; panel boot only; do not scope FilamentView to the PanelProvider class — LAYOUT_END scopes are page classes). Org Map (`clarity-scout-birds-eye`) mounts the same island next to `#clarity-scout-app` and boots via `mountOtto` in `birdseye.js`. Driver PWA stays Otto-free.

## Datadog cost logging (DEV-2709)

Production-only DogStatsd via `App\Support\Otto\OttoMetrics`. Gate: `app()->isProduction()` and `config('services.datadog_forwarding')` (`DATADOG_FORWARDING`). QA and local stay silent. Schema matches Guardian Otto (`insight-lpr/overwatch` `App\Support\Otto\OttoMetrics`); the product prefix is `clarity.` so Clarity turns do not land on `overwatch.otto_*`.

| Metric | Type | When |
|---|---|---|
| `clarity.otto_message` | count | Each completed model turn (`RunsOttoStream`, after `onStreamComplete`) |
| `clarity.otto_tokens_prompt` | count | `Usage::promptTokens` when > 0 |
| `clarity.otto_tokens_completion` | count | `Usage::completionTokens` when > 0 |
| `clarity.otto_estimated_cost_usd` | count (float) | `(prompt/1e6)*rate_in + (completion/1e6)*rate_out + (cache_read/1e6)*rate_cache` from `config/otto.php` `pricing`. Cache reads use `Usage::cacheReadInputTokens` and are not a separate metric |
| `clarity.otto_tool_call` | count | One per tool call on that turn (`surface` + `tool` tags only) |
| `clarity.otto_feedback` | count | Thumbs set (`rating` `positive`/`negative`). Clearing a thumb does not emit |

Message, token, and cost metrics are tagged `surface`, `user_id`, and `user` (sanitized email). Never `org_id`. Guardian's `overwatch.otto_active_users_24h` gauge is not ported: it is a Postgres `public.add_metric` cron against the `overwatch` schema, which Clarity does not have.

## Local realtime + Horizon

- **Broadcast:** `BROADCAST_CONNECTION=pusher` → lerd Soketi (`PUSHER_HOST=lerd-soketi:6001`). Browser: `VITE_PUSHER_HOST=localhost`, port `6001`, scheme `http`. Local Echo in `resources/js/app.js` **hard-codes** `forceTLS: false` / `enabledTransports: ['ws']` and patches `Pusher.Runtime.getProtocol` to `'http:'` — pusher-js 8 ignores `forceTLS:false` on HTTPS pages (`https://platform.test`) and would otherwise open `wss://localhost:6001`. Do not proxy `/app/` to Soketi — Filament is `/app`.
- **Queue:** `QUEUE_CONNECTION=redis` (not `sync`) so `RunOttoChat` hits Horizon `{otto}`.
- **Workers:** `lerd worker` Horizon + Vite for platform; confirm supervisor `*-supervisor-otto` shows `redis:{otto}`. After Horizon/config changes, restart the Horizon worker — a process started before `supervisor-otto` will not pick up `{otto}`.
- **Horizon 5.46 vs Laravel 12.66:** `horizon:work` must declare `--stop-when-empty-for` or every worker crashes on boot and jobs sit pending while supervisors look "running". Shim: `App\Horizon\WorkCommand` (remove once Horizon is >= 5.47). Redis `retry_after` is 300s so it stays above Otto's 180s timeout.
- **Broadcast auth vs catch-all:** `POST /broadcasting/auth` comes from `bootstrap/app.php` `->withBroadcasting(..., ['middleware' => ['web']])` (`app->booted()`). The `{any}` → `/app/login` catch-all is registered in `AppServiceProvider` on a **later** `booted` callback so it cannot steal Echo auth. If the catch-all wins, Echo 302s to login, never joins the private channels, and the UI stays on "Thinking…" after `RunOttoChat` finished. Scout’s `/api/broadcasting/auth` is Sanctum-only and does not cover Filament Otto.
- **Thinking hang-net:** Vue `OttoChat` polls `POST /otto/conversations/{id}/poll` (~1.5s) while `thinking`. `pending` and `idle` keep polling until `complete` or 180s. Completion counts raw assistant rows (same count stored at send), so an empty historical row cannot freeze the turn at `idle`. When the job forgets `otto:pending_prompt:{id}` and a new assistant row exists, poll returns structured messages (raw content + markers, no Blade HTML). Stream tokens still win when Echo works. `stream_end` stops that poll *before* `persistInvestigation` stamps `search.messageId`, so a live reply can land with no result table; `.otto.investigation.updated` then calls `graftWidgetsFromServer()` to copy marker-injected widgets into the live bubble.
- **Vue bootstrap:** `#otto-root` + `window.__OTTO_CONFIG__` (`userId`, initials/color, avatars, optional `conversationId`, `hasMessages`, `showDisclaimer`). `filament.js` remounts on `livewire:navigated` if that node was replaced. The list endpoint also returns `activeConversationId`. `GET /otto/conversations/{id}` writes that session key; `POST /otto/conversations/reset` (close / new chat) forgets it. Org Map registers a generic `scout-map` page context (description only) — no `otto-pan-to` listener and no investigation overlay on ScannerMap.
- **Beta disclaimer:** shown over the chat column as soon as the panel opens, before a message can be sent. Acceptance is `session('otto_disclaimer_accepted')` (`POST /otto/disclaimer`), so it lasts for the login session and comes back on the next one. A later history refresh must not pop it again after "I understand".
- **Send path:** one Enter → one optimistic user bubble + one `POST /otto/conversations` (or `.../{id}/messages`). Fetches send `X-Socket-ID` so `OttoUserMessagePosted` `->toOthers()` skips this tab. JS `onUserMessage` also ignores the sender’s own prompt (`lastSentPrompt` / last user bubble). `OttoConversation::send()` no-ops while `otto:pending_prompt:{id}` is set. Composer `thinking` is locked **before** painting the bubble. History search escapes `%`, `_`, and `\` before `ilike`. Assistant markdown (live and reload) is the Vue renderer: headings, links (`http`/`https`/`mailto`/same-origin), fenced code, lists, bold, italic. Thumbs persist on the assistant row's `meta.feedback` via `POST /otto/conversations/{id}/messages/{messageId}/feedback`.

## Behavior (chat only)

- Transient in-memory `Investigation`; persisted `AgentInvestigation` keyed by `(user_id, conversation_id)`
- Hit Search (DEV-2318) uses `HitsListQuery` for access control (user kits, NICB/OverWatch exclusion), `PlatePattern` for `*` wildcards, `forScannedBetween`, and the Hits-page actionable dispositions (`actionableDisposition()` on ClickHouse; New Hit + Accessible on Postgres) — do not invent a parallel hit query
- Scan and hit search may run with **only a time range** (or the default last 30 days). Plate, driver, and kit are optional. Do not ask the user to add one of those to “narrow” a recent/today request. The system prompt and tool descriptions say this explicitly so the model does not refuse a date-only search.
- **Fabrication guard:** `FabricationGuard` runs at the end of `RunOttoChat` before the page-action buffer is pulled. A reply that asserts results ("here are the 50 most recent scans") or a filter proposal is discarded unless this run recorded a `Search` or a `PageAction`. A tool-call event is not proof — a call that recorded nothing still counts as fabricated, and searches from earlier turns do not excuse a fresh claim. The fabricated user+assistant rows are deleted, `otto.reply_discarded` drops the live bubble, and one corrective re-run gets `CORRECTION_NOTE` in the system prompt. The pending-prompt key stays set across that re-run. A second fabrication is replaced in place with `FabricationGuard::UNFULFILLED_ACTION_RESPONSE` (`otto.reply_replaced`) instead of looping.
- Search tools (`ScanSearchTool`, `HitSearchTool`, `HotlistSearchTool`) always `LIMIT` to `LimitedToolResultMessage::SEARCH_LIMIT` (50) and persist at most that many result IDs. They never run a warehouse `COUNT(*)` / `count()` on scans, hits, or hotlist. Tool **descriptions** say “a page of the most recent matches” and must not mention 50 / `SEARCH_LIMIT` / “there may be more” (those leak into every turn and the model copies them). Tool **result** copy uses “most recent N” for the returned page only — never “I found N” and never a corpus total. N is `count($resultIds)` after the same `capResultIds` pass that is stored for the widget (cheap collection count, not SQL). Cap / “there may be more” is mentioned **only** when N equals `SEARCH_LIMIT`. When N is below the cap (e.g. 17), the tool string says 17 and must not mention 50, a cap, a limit, or that more may exist. `GET /otto/investigation/{id}` hydrates at most `SEARCH_LIMIT` IDs **per search** (legacy conversations that stored more are truncated) and JSON has no `total` / `recordCount`. The chat widget labels the page “N most recent”, never “N records”.
- Widget markers / `MessageRenderer` for scan|hit|hotlist|zone tables and the scout_driver static-map island; `RunOttoChat::persistInvestigation()` stamps `search.messageId` **and** writes `<!--otto_table:{type}:{searchId}-->` onto that assistant row. `OttoConversation::injectSearchMarkers()` is the reload fallback for older rows that only have the investigation stamp. Unmatched / empty message IDs are skipped — never attached to the latest reply (that leaked prior hit tables onto a later driver follow-up). Live path: Echo `.otto.widget` records the widget on the in-flight turn, but `showStreamResultWidgets` keeps the results table (and the other stream result widgets) hidden until that turn finishes, so a search does not paint an empty table while Otto is still writing. The widget also stays on “Loading results…” until this search id is in the investigation payload — a conversation that was already loaded is not treated as ready. Poll/reload **and** `.otto.investigation.updated` → `graftWidgetsFromServer()` hydrate the widget when Echo missed `.otto.widget`. Both paths reconcile through `mergePolledThread()` in server (refresh) order: the follow-up user message, then that turn's assistant reply and its results table. A new reply is appended; its table is not grafted onto an earlier assistant just because the thread already has one. Report affordances always off. Clicking the driver map opens popout fullscreen (`otto-open-fullscreen`) when compact; already-fullscreen chat uses a default cursor and ignores the click. Zone rows link to `ManageZones` (`?zone=id`) or pan to the centroid on the fullscreen map.
- `HotlistSearchTool` looks up assignments (wanted vehicles) via ClickHouse `Hotlist::visibleToOrg()` (direct `forOrg` plus staged rows from `Org::stagingOrgIds()`). No default date window. Unknown statuses return a valid-status list instead of an unfiltered search. Hit search remains for match events.
- Hover on a result row opens the Overwatch-style detail popover (`components.otto.detail-popover`) via `otto-show-detail` / `otto-hide-detail`. Opening the compact History list (`otto-history-open`) or switching conversations (`otto-dismiss-popups`) closes that card and any map popup immediately, and hover popups stay suppressed until History closes. That event must **not** clone a Hit/Scan Detail card into the chat thread — chat cards come only from Echo `.otto.detail` (`ShowResultDetailsTool`).
- Fullscreen popout shows the Overwatch-style results pane (`components.otto.investigation-results-pane`): Google Map + search legend + scan/hit/driver/plate filters + table. Hidden in compact popout until fullscreen. The history column can be collapsed on demand (`localStorage` key `otto-history-collapsed`). While it is collapsed the sidebar is unmounted so chat and the results pane keep the width, and the sidebar **New** button moves to the chat-column header beside **Expand history** — it is not duplicated and not left inside the closed column. Expanding restores **New** to the sidebar header. The pane is `wire:ignore` (like the message list) so a `send()` morph does not `display:none` the map host. Row click pans (`otto-pan-to`); chat widget rows use the same event. Map popups are a custom `OverlayView` on `floatPane` (`fromLatLngToDivPixel` at the pin LatLng) — never `google.maps.InfoWindow` / `open({ anchor: marker })`. SVG data-URI pins report a 300×150 intrinsic size and InfoWindow parks the popup miles from the marker. Filament loads `Vite::asset('resources/js/app.js')` from `public/build` unless `public/hot` exists; source-only edits do not reach the browser.
- System prompt: Clarity product voice — no Guardian Investigate / case numbers / convoy / officer language. Result phrasing is “most recent N”, never “I found N” or a warehouse total. N comes from **this search’s own tool result**. Prompt examples use a non-cap count (12) and must not include a “50 most recent / there may be more” template. Mention “may be more” only when that tool result itself says the page was capped.
- Knowledge articles must not mention ClickHouse, Postgres, CDC, impersonation, or RDN internals

## Timezones

Otto jobs run on Horizon `{otto}` with **no** `auth()->user()`. Tools must use `$this->user->timezone` (`dti.timeZone`, default `America/Chicago`), never `auth()->user()?->timezone`.

- **Prompt:** `resources/views/ai/otto/system-prompt.blade.php` injects `now` in the user zone. The model must never do TZ math — pass wall-clock `start_date`/`end_date` using the numbers the user said; append a UTC offset **only** when the user names a zone (`"6:43pm CDT"` → `2026-05-26T18:43:00-05:00`; naive `"3pm"` stays `2026-06-12T15:00:00`). Duration arithmetic against prompt “now” is not a TZ conversion. Display times in the user zone. Never snap a relative window to a preset (`"last 4 days"` must not become `last_7_days`).
- **`UserRequestedTimeRange`** (`app/Support/Otto/UserRequestedTimeRange.php`, wired in `ResolvesOttoDateRange::requestHonoringUserTimeRange` via `Investigation::activePrompt` set in `RunsOttoStream`): when the latest user prompt names a relative/“today” window, that window **overrides** the model’s `time_range`/`start_date`/`end_date`. Exact presets are `today`, `yesterday`, `last_7_days`, `last_30_days`, `last_90_days` (aliases `7d`/`30d`/`90d` still parse). Custom bounds are emitted as ISO-8601 **with offset** so a later `parse(...)->setTimezone('UTC')` cannot treat wall clock as UTC.
- **`ResolvesOttoDateRange`:** naive timestamps are parsed in the user zone (an explicit offset still wins). Date-only values expand to local start/end of day. Results are ISO-8601 with offset. Custom future *datetime* ends clamp to now; date-only “through today” stays end of the local day.
- **Hit search:** converts those ISO bounds with `convertToUtc($start, $tz)` before `HitsListQuery` / `forScannedBetween`. Those helpers also call `convertToUtc` and would otherwise treat naive strings as UTC when auth is missing (queue-worker miss: UTC calendar “today” vs Chicago “today”).
- **Scan / hotlist:** `between($start, $end, $tz)` parses with the user zone; an offset in the ISO string still wins. Scan hot-vs-cold uses the UTC instant of `start`.
- **Page filters:** Apply* tools reuse `ResolvesOttoDateRange` / `UserRequestedTimeRange` (queue-safe `$this->user->timezone`). Custom ranges are ISO-8601 **with offset**. Filament adapters store naive `Y-m-d H:i:s` in the user TZ for DateTogglesFilter pickers. HTTP apply may use `auth()->user()->timezone` (same user).
- **Widgets:** `InvestigationDataController::formatScannedAt` converts stored UTC `scanned_at` to `'M d, Y h:i A T'` in the **user** timezone (Clarity `scans_hot`/`scans_cold` have no camera tzid). Scout `last_seen_at_utc` stays ISO-8601 so minutes-ago stays correct. Frontend `fmtTime` prints the preformatted string as-is.

## Page context (scans / hits / hotlist)

Orthogonal to `Surface`. `PageContext` (`pageType`, `description`, `state`) is a **hint**, never auth.

**Pages:** `/app/scans` → `scan-search`, `/app/hits` → `hit-search`, `/app/hotlists` → `hotlist-search` (path aliases also accept `/scans`, `/hits`, `/hotlists`, `/app/hotlist`).

**Read path:** `resources/js/otto/page-context.js` (`window.Otto`) ← Filament `InteractsWithOttoPageActions` re-registers after each render → Vue `send()` ships `currentPageContext()` with `POST /otto/conversations*` → `OttoConversation::send` → `RunOttoChat` → `PageContext::fromClient`. Org Map registers `scout-map` (unactionable; in-chat search still runs).

**Write path:** Apply* tools `ProposesPageActions` → broadcast `OttoPageActionProposed` (`otto.page_action`) → chip in chat → Accept → `Livewire.dispatch('otto-page-action')` → page adapter applies after `ottoPageActionAuthorized()` (`OttoAccess` + `ViewAny_SCAN` / `ViewAny_Hit` / `ViewAny_Hotlist`).

**Deferral:** `ScanSearchTool` / `HitSearchTool` / `HotlistSearchTool` implement `PageAwareTool` + `DefersToPageSearch`. On the matching page they **forward** into Apply* (no in-chat results) **before** incrementing the tool-call budget. Hotlist is the exception: a **date-only** request cannot be expressed as page filters (the Hotlist table has no date toggles), so that chat tool may still run. Escape hatch: `OttoConversation::send` **strips** page context for “Make Otto search instead” (`SEARCH_INSTEAD_PROMPT_*`) or `InChatSearchIntent` phrases.

**Filament mapping:** Scans `filters.ocr` / `filters.kits` / `filters.flexsearch` / `filters.invalid` / `scanned_at`; Hits `filters.scan.ocr`, VIN/order, status, hit type, kits, clients, flexsearch, and **time_range applied to both** `hits.created_at` and `scans.scanned_at` (scanned-date has no yesterday toggle / no advanced); Hotlist plate/VIN/order/status/clients/flexsearch/missing_plate — no dates. ListScans must `applyTableFilters()` so `searchApplied` becomes true. DateTogglesFilter keys on Scans/Hits are `today` / `yesterday` (scans only) / `last_7d` / `last_30d`. Otto tool args stay `today` / `yesterday` / `last_7_days` / `last_30_days` / `last_90_days` (aliases `7d`/`30d`/`90d`); Apply* maps those onto the Filament key for Accept/Re-Apply. `last_90_days` has no matching toggle, so the payload is a custom `{start,end}` ISO range.

**Chip copy:** `PageActionChange.summary` is what the Search card / Re-Apply chip renders. It must be a human phrase ("Set the time range to the last 7 days", "Set the status to Closed Positive") — never a Filament toggle key (`last_7d`), Otto preset slug (`last_7_days`), payload field (`time_range`), raw enum name (`Staging_Live`), or ISO timestamp. Phrases live in `App\Support\Otto\PageActionCopy`. `value` stays the canonical apply payload. Vue `page-actions.js` also rewrites leftover slugs on restored cards. Page-state injected into the system prompt humanizes the same time-range tokens so Otto does not echo them.

**Prompt:** `resources/views/ai/otto/fragments/page-context.blade.php` when a `PageContext` is present; `$pageHasActions` from any resolved tool with `availableOnPage(null) === false`. Record-type routing: scans page = scans only; hits = hits only; hotlist = assignments only. On an unactionable page (Company Metrics / dashboard) the fragment must say Otto **cannot change the page** but **must still search** for live records — never treat “no page capabilities” as “no ScanSearchTool”, and never substitute `KnowledgeBaseSearchTool` for “today’s scans”.

**Off-page record search:** “Show me today’s scans” (or hits / assignments) on Company Metrics or Org Map is a normal `ScanSearchTool` / `HitSearchTool` / `HotlistSearchTool` call in the laravel/ai loop — same as Overwatch. On the matching search page those tools still defer to Apply*. The prompt must say Otto **cannot change** an unactionable page but **must still search** in chat; never treat “no page capabilities” as “no ScanSearchTool”. `KnowledgeBaseSearchTool` refuses when `RecordLookupAsk` matches the user prompt so a first turn cannot substitute docs for `ScanSearchTool`. `GET /otto/conversations/{id}` orders by message `id` (uuid7), not `created_at` — laravel/ai writes the user + assistant in the same second. `MessageRenderer` / Vue `markdown.js` `stripToolCalls` drop invented `[Calling …]` stand-ins if a model turn leaks one. Vue queues a late `.otto.widget` until `stream_start` so a leftover `pending` bubble cannot appear.

**Persist:** `Investigation::recordProposedPageAction` / `pullProposedPageActions`; `RunOttoChat` writes `meta.page_actions`; `GET /otto/conversations/{id}` returns `page_actions` on the assistant row. Search-instead user rows render as a Vue `SearchInsteadMarker`.

**Wiki (after merge):** update `okf/concepts/otto.md` for page context + Apply* tools. Do not edit `okf/` in this change.

## Scout zones (DEV-2320)

Zones live in PostgreSQL `platform.zones` — not ClickHouse. Otto searches, proposes creates, and proposes attribute updates (no-scan / ZIPs / color / description / assignments); delete and map-polygon edit stay on the map editor. There is no Zones-list page-filter adapter in this ticket (in-chat search always runs).

- **Access:** `ZoneSearchTool`, `ProposeCreateZoneTool`, and `ProposeUpdateZoneTool` register for every Otto user (`authorizedFor` returns true) so the model can relay a soft message. `OttoScoutAccess` is the shared gate (also used by `ScoutDriverPositionTool`). Horizon restores `admin_impersonator` in `RunsOttoStream` (stamped on `RunOttoChat`). Split copy: no Scout → ask the account manager; Scout but not ADMIN → “Zone search and creation are limited to organization admins.” Impersonation bypasses the Scout flag only — ADMIN is still required.
- **Search:** `Zone::forOrg` on PostgreSQL. Filters: name (partial `ilike`), `is_no_scan_zone`, assigned driver name (`whereHas` users). Soft-deletes hidden. Cap `LimitedToolResultMessage::SEARCH_LIMIT` (50); phrase “most recent N”. Records `SearchType::Zone` + ids; widget type `zone`. The system prompt requires `ZoneSearch` on the same turn as “what zones do I have?” (and no-scan / assignment questions). Replies must not name tools or claim zone search is unavailable. The customer article `asking-otto-for-help` must not say zones cannot be searched.
- **Create:** propose → user Accepts → server persist. The tool never writes. Valid ZIPs (checked against `tiger_data.zcta5_all` via `ZipCodeLookup`) and not `open_map_editor` → `PageAction` `pageType = zone-create`, `name = create-zone`. Draw / no ZIPs → `name = open-zone-editor`. Missing name or empty shape: ask in chat, do not propose. Unknown ZIPs or unresolvable assignee names abort the proposal. No-scan always stores `Zone::NO_SCAN_COLOR`. Never invent GeoJSON polygons.
- **Same-name guard:** if the org already has a zone whose name matches case-insensitively, `ProposeCreateZoneTool` proposes `update-zone` instead of `create-zone`. `POST …/zone-create` Accept also updates that row instead of inserting a duplicate. The system prompt tells the model to prefer `ProposeUpdateZone` for modifications (“make it a no-scan zone”).
- **Update:** `ProposeUpdateZoneTool` → `PageAction` `pageType = zone-update`, `name = update-zone`. Identify by `zone_id` or exact name. Omitted fields keep current values; empty `zip_codes` keep the existing boundary (including polygons). Accept: `POST /otto/conversations/{id}/zone-update` via `PersistZone::update` (same auth/geometry path as create).
- **Accept:** `POST /otto/conversations/{id}/zone-create`, `.../zone-update`, and `.../open-zone-editor` (not a Filament page adapter — ManageZones is usually not mounted). Re-validates ZIPs, color, assignees, org. Persist via `PersistZone` (same path as `ManageZones::save()`: geometry rebuild, assignment sync, driver broadcasts, analytics with `ScoutAnalyticsPage::Otto`). Then records the zone id on the investigation and broadcasts `OttoInvestigationUpdated`. `open-zone-editor` returns `ManageZones::getUrl()` with draft query params (`name`, `description`, `color`, `no_scan`, `zips`); JS navigates. Vue branches Accept for these action names onto the HTTP endpoints instead of `otto-page-action`.
